OpenClaw Local-Only Code-Along

This page is the workshop guide for the repo. The flow is: data intake review → operational memory → offline communications triage. Everything here stays in local folders and produces reviewable markdown artifacts.

Local files only No live integrations Copy/paste prompts Markdown outputs

Before starting

~3 min

Open these side by side

  • This runbook
  • OpenClaw web UI
  • This repo folder in your IDE or terminal if you want to inspect files directly

Repo areas used in this session

  • code-along/01-data-intake-review/
  • code-along/02-operational-memory/
  • code-along/03-offline-communications-triage/
Session framing: the runbook is the primary guide for the workshop. You can work straight from the prompts here, and optionally use your IDE or terminal to inspect the folders as you go. The pattern throughout the workshop is simple: files go in, prompts run locally against those files, and markdown artifacts come out.

Exercise 1 — Data intake review

~10 min

Goal: turn unknown files into a trustworthy intake report.

Starter files

  • incoming/customers.csv
  • incoming/orders.csv
  • incoming/events.jsonl
1. Paste this prompt into OpenClaw
Review the files in `incoming/` and create a markdown intake report in `outputs/`.

Your job is flagging and documenting, not cleansing.

Include:
- files reviewed
- schema fingerprint
- sanity flags
- draft data dictionary
- questions to ask before use
- recommended next checks

Constraints:
- do not modify source files
- do not make statistical claims beyond what can be directly observed
- do not recommend value-altering fixes
- be explicit when something is ambiguous
2. Optional: inspect the starter files in your IDE or terminal
cd code-along/01-data-intake-review
ls incoming
cat prompts/intake-review.md
3. Let OpenClaw generate the report and review the output in outputs/intake-review.md

You should see

  • a markdown report in outputs/
  • schema fingerprint
  • sanity flags
  • draft data dictionary
  • questions before use
Key boundary: this exercise documents and flags issues. It does not cleanse data or alter source values.
Optional stretch: add another CSV with one or two messy columns and rerun the report.

Exercise 2 — Operational memory

~12 min

Goal: turn work residue into daily and weekly momentum docs, then put one of those docs on a schedule with cron.

Starter files

  • inbox/2026-04-21-standup.md
  • inbox/release-draft.md
  • inbox/customer-feedback.txt
  • inbox/roadmap-bullets.md
1. Paste one of these prompts into OpenClaw
2. Optional: inspect the starter notes and prompt files in your IDE or terminal
cd ../02-operational-memory
ls inbox
cat prompts/daily-log.md
cat prompts/weekly-hype.md
Date window: the daily prompt and the cron example below use the same behavior spec so scheduled runs behave the same way as manual runs. The weekly prompt is scoped to the current calendar week. If notes are missing for some days, the output should summarize only the available evidence and note partial coverage instead of inventing filler.
3. Generate the daily log
Review the notes in `inbox/` and generate today's operational memory log in markdown in `outputs/`.

Time window:
- use only notes that belong to today
- use filenames first to determine date when possible
- use file contents as a secondary signal if needed
- ignore older notes unless a note from today explicitly references them

Focus on:
- progress
- blockers
- notable decisions
- likely next steps

Constraints:
- keep it concise and grounded
- make it useful to a manager or teammate
- cite filenames when helpful
- do not invent work that is not supported by the files
- if there are no notes for today, do not invent a log; instead state briefly that no entries were captured today
- if today's notes are sparse, summarize only the available evidence and note that coverage is partial
4. Generate the weekly hype doc
Review the notes in `inbox/` and generate a weekly hype doc in markdown in `outputs/`.

Time window:
- use only notes from the current calendar week
- use filenames first to determine which notes belong to the current week
- use file contents as a secondary signal if needed
- ignore older notes unless a note from the current week explicitly references them

Include:
- wins
- momentum
- notable changes
- risks
- blockers
- next bets

Constraints:
- keep the tone crisp and upbeat
- stay evidence-based
- do not exaggerate impact
- if notes exist for only part of the week, summarize only the available evidence and briefly note that coverage is partial
- do not invent missing daily activity or unsupported progress
5. Set up a cron example
Create a cron job named "code-along daily log".

Schedule:
- Run every day at 9:00 AM
- Time zone: America/Chicago

Task:
Review the notes in `inbox/` and generate today's operational memory log in markdown in `outputs/`.

Time window:
- use only notes that belong to today
- use filenames first to determine date when possible
- use file contents as a secondary signal if needed
- ignore older notes unless a note from today explicitly references them

Focus on:
- progress
- blockers
- notable decisions
- likely next steps

Constraints:
- keep it concise and grounded
- make it useful to a manager or teammate
- cite filenames when helpful
- do not invent work that is not supported by the files
- if there are no notes for today, do not invent a log; instead state briefly that no entries were captured today
- if today's notes are sparse, summarize only the available evidence and note that coverage is partial

You should see

  • outputs/daily-log.md
  • outputs/weekly-hype.md
  • a grounded summary of progress, blockers, and next steps
  • a sharper weekly summary with wins, risks, and next bets
  • a saved cron job for repeatable generation
Default automation path: for this exercise, cron is part of the standard flow because the schedule is known ahead of time.

Useful file to inspect

cat schedule/cron-examples.md
cat schedule/heartbeat-note.md

Optional stretch

Add one more note to inbox/ with a blocker or a win, then regenerate the daily or weekly output or update the cron to target the weekly doc instead.

Exercise 3 — Offline communications triage

~10 min

Goal: turn exported mail into an action list.

Starter files

  • eml/001-webinar-speaker-confirmation.eml
  • eml/002-security-review-followup.eml
  • eml/003-room-change.eml
  • eml/004-fyi-recording-policy.eml
  • eml/005-demo-repo-status.eml
1. Paste this prompt into OpenClaw
Review the `.eml` files in `eml/` and produce an action-oriented markdown triage report in `outputs/`.

Extract:
- likely action items
- deadlines or date mentions
- waiting-on items
- low-priority or FYI messages
- ambiguity notes

Constraints:
- be careful with uncertainty
- do not modify source files
- do not send replies
- this is offline triage from exported mail archives
2. Optional: inspect the starter messages in your IDE or terminal
cd ../03-offline-communications-triage
ls eml
cat prompts/email-triage.md
3. Let OpenClaw generate the triage report and review the output in outputs/email-triage.md

You should see

  • a markdown triage report in outputs/
  • action items
  • deadlines and date mentions
  • waiting-on items
  • low-priority / FYI items
  • ambiguity notes
Key boundary: this is offline triage from exported mail archives. It does not send replies or connect to live mail.
Optional stretch: add one more exported message with an ambiguous ask and rerun triage.

Post-session / extra credit

Optional

These are good follow-ups after the workshop if you want to automate the same local-folder patterns on your own time.

Heartbeat idea: periodically notice new files

Use this when you want the agent to periodically check a folder and produce a report only when new files appear or something changes.

Watch the folder code-along/01-data-intake-review/incoming as part of a heartbeat-driven workflow.
If new files appear, review them and create or update outputs/intake-review.md using prompts/intake-review.md.
If nothing has changed, stay quiet.

Cron idea: generate artifacts on a schedule

Use this when the schedule is known ahead of time, like a daily log or a weekly summary.

On a daily schedule, work in code-along/02-operational-memory.
Read the files in inbox/ and generate outputs/daily-log.md using prompts/daily-log.md.

On a weekly schedule, read the same inbox/ folder and generate outputs/weekly-hype.md using prompts/weekly-hype.md.
Recommended pattern: manual run first, make cron part of the default workflow when the schedule is known, and use heartbeat for periodic noticing.
